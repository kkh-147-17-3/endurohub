# 기술적 도전과 의사결정

실서비스를 운영하며 마주친 문제 중, 설계 수준의 판단이 필요했던 것들만 정리했다. 각 항목은 결론 먼저.

---

## 1. LLM 크롤링 파이프라인 — 비용·환각·신뢰성을 통제 가능하게 설계

**LLM은 "페이지에서 값을 읽는" 마지막 단계에만 쓰고, 탐색·검증·반영은 결정론적 코드와 사람이 담당하는 구조로 설계했다.**

대회 정보(참가비·일정·코스)는 사이트마다 위치가 제각각이라 — HTML 텍스트, 포스터 이미지, JS 모달 —
셀렉터 기반 파싱만으로는 커버가 불가능했다. Playwright + LLM(vision 포함) 조합으로 풀되,
매일 수백 건을 도는 자동화 잡이 되려면 세 가지를 통제해야 했다.

- **비용** — 하위 페이지 탐색을 LLM 에이전트에 맡기지 않고 결정론적 키워드 스코어링으로 처리해
  대회당 LLM 호출 수에 상한을 뒀다. 실행 시간과 비용이 예측 가능해야 스케줄 잡으로 운영할 수 있다.
- **환각** — 오류의 비대칭성을 기준으로 검증 강도를 이원화했다. 접수 마감 판정처럼 **근거를 기계적으로
  검증할 수 있는 판단**(LLM이 인용한 문구가 실제 페이지에 존재하는지 확인)만 자동 반영하고,
  참가비처럼 "그럴듯한 오답"을 걸러낼 수 없는 추출은 관리자 승인 게이트를 거치게 했다.
- **성공률** — 초기 실측은 0/10. 원인은 vision 성능이 아니라 **정보가 "요강" 하위 페이지의 텍스트에
  있다는 것**이었다. 텍스트 우선·이미지 폴백으로 경로를 재설계해 7/10으로 끌어올렸다.
  "모델을 더 잘 쓰는 것"보다 "모델이 덜 필요한 경로를 찾는 것"이 정답이었다.

## 2. 자동 수집 ↔ 운영자 수작업 충돌 — Human-in-the-loop 파이프라인

**크롤러에게 기존 데이터의 직접 쓰기 권한을 주지 않는 것으로 자동화와 데이터 신뢰성을 공존시켰다.**

매시간 도는 크롤러가 운영자가 손으로 다듬은 데이터를 덮어쓰는 문제를, 권한 설계로 풀었다:
크롤러의 변경은 "제안(`RacePendingChange`)"으로만 적재되어 관리자가 승인해야 반영되고,
관리자가 어드민에서 수정한 필드는 자동으로 잠겨(`locked_fields`) 크롤러가 건드릴 수 없다.
승인 대기 건수를 어드민 뱃지로 노출해 검수가 운영 루틴에 자연스럽게 편입되도록 했다.

## 3. SSR 아키텍처 — 렌더링 경로와 네트워크 경로의 분리

**같은 API를 서버는 내부망으로, 브라우저는 프록시로 호출하는 이중 네트워킹 구조를 잡고, 캐시를 2단으로 쌓아 TTFB를 확보했다.**

SEO가 중요한 콘텐츠 서비스라 SvelteKit SSR + Django API로 프론트/백을 분리했다.
SSR load는 nginx를 거치지 않고 내부 네트워크로 Django에 직행하고(`http://api:8000`),
브라우저 호출만 nginx가 `/api/*`로 프록시한다 — API 클라이언트를 서버용/브라우저용으로 분리해 구현.
성능은 Django 캐시(홈·연관 대회 등 무거운 집계) + SvelteKit SSR 인메모리 캐시의 2단 구성으로 잡았다.

## 4. 인증 — "로그인 없이 쓸 수 있는 서비스"에 맞춘 최소 설계

**서비스 성격(조회가 90%)에 맞춰 세션·CSRF 흐름을 통째로 배제하고, 익명 참여 + 경량 JWT + OAuth의 3단 구조를 택했다.**

게시글·댓글은 로그인 없이 작성하고 작성 시 비밀번호(bcrypt)로 본인 확인, 좋아요·후기는 IP 해시로
중복만 방지한다. OAuth(카카오·네이버·구글)는 즐겨찾기·알림 같은 개인화 기능에만 요구하며,
토큰은 페이로드에 `user_id`만 담는 JWT라 SvelteKit SSR과의 결합이 단순하다.
인증 요구 수준을 기능별로 차등화한 것이 커뮤니티 초기 참여 장벽을 낮췄다.

## 5. 1인 운영을 위한 관측성과 운영 자동화

**"문제를 사용자보다 먼저 아는 것"을 목표로, 계측 → 수집 → 알림까지의 관측성 스택을 직접 구축했다.**

OpenTelemetry 계측 + Grafana LGTM 스택으로 메트릭·로그·트레이스를 수집하고, nginx 액세스 로그를
JSON 구조화해 트래픽·봇 차단 현황을 대시보드로 분석한다. 500 에러는 Telegram으로 실시간 알림
(동일 에러 60초 중복 억제). 배포는 GitHub Actions self-hosted 러너로 자동화하고 변경된 컨테이너만
선택적으로 재빌드한다. Sentry·PostHog·GA까지 포함해, 혼자서도 실서비스의 상태를 놓치지 않는
운영 체계를 만들었다.
